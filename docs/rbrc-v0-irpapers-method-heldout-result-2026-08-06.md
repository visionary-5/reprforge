# RBRC v0：IRPAPERS 方法未见域结果

日期：2026-08-06  
协议冻结提交：`37c4c31`  
判定：**质量 PASS，成本 NO-GO，整体盲测 FAIL；未修改 v0 参数**

## 1. 证据边界

本结果在 `configs/rbrc-v0-frozen-2026-08-06.json`、编译器、评测器和 BM25→ColPali
校准证书提交之后生成。评测器核验的规范化配置 SHA-256 为
`deafdc17a11604e124b5c05564756e43911f91de23d7d9c70b3aa51f15cd0103`。

IRPAPERS 的 180 个查询和 3,230 页没有参与 RBRC v0 的规则与阈值设计，因此是本方法的
即时 held-out transfer；但它曾用于 ReprForge 早期检索实验，不能包装成论文最终的
全局 sealed test。最终主盲测仍是协议已经锁定的 Energy FR 和 Physics FR。

校准阶段只使用 HR 和 Finance EN。正式冻结证书选择 `Guard(40,50,B=40)`；所有静态
Top-20/30/40 均未通过质量门，因此“仅安全编译”消融必须全局 abstain 到 Top-50。

## 2. 核心结果

主缓存统一为容量 20% 语料页的 LRU，统计原始顺序加 50 个固定随机排列。

| 方法 | nDCG@10 平均损失 | 违规率 | 冷页/查询 | 相对 Top-50+LRU | Abstain |
|---|---:|---:|---:|---:|---:|
| 固定 Top-50 | 0 | 0 | 20.634 | — | 0% |
| 仅安全编译 | 0 | 0 | 20.634 | 0% | **100%** |
| 仅驻留感知，Guard-20 | **-0.000090** | 0.120% | 19.919 | -3.47% | 0% |
| 完整 RBRC，Guard-40 | 0.000063 | 0.044% | 20.436 | **-0.96%** | 0% |

正的损失表示比固定 Top-50 差；负数表示略好。完整方法的平均损失远小于冻结的 0.002
边界，平均违规率也远小于 5%，51/51 个顺序都比 Top-50+LRU 少冷 miss。因此质量和
顺序方向性通过。

但是完整方法只减少 0.96% 冷读取，显著低于预注册 10% 门槛。无质量约束的 Guard-20
也只减少 3.47%，说明问题不只是安全证书把 floor 提高到 40；这个工作负载本身没有足够
的动态深度收益。

完整方法在顺序间的冷页标准差为 0.352，p05/p95 为 19.986/20.883；平均损失的
p05/p95 为 -0.000193/0.000385。跨所有顺序出现过的最差单查询损失为 0.13093，但
worst-5% CVaR 的顺序均值为 0.00171、最大值为 0.01455。平均质量很稳并不等于逐查询
保证，因此这组尾部数值必须与平均值同时保留。

## 3. 强缓存对照

| 固定 Top-50 缓存 | 冷页/查询 |
|---|---:|
| LRU | 20.634 |
| 等页成本 GDSF | 18.654 |
| LFU | **17.602** |
| Belady future-aware oracle | 12.182 |

完整 RBRC 的 20.436 冷页比固定 Top-50+LFU 多 16.1%，比 GDSF 多 9.6%。所以本域结果
不能写成“规划器优于强缓存”；强缓存仅通过更好的保留策略，就超过了当前 RBRC 改变
查询深度的收益。

Belady 与 LFU 之间仍有约 5.42 冷页/查询的未来信息差距，但这不是允许 v0 增加预测器或
RL 的理由。Belady 仍只作为非部署上界。

## 4. 失败模式意味着什么

IRPAPERS 的固定 Top-50 在 20% LRU 下平均只产生 20.63 个冷页，远低于每查询请求的
50 页。这说明候选页在查询间高度复用，Top-50 中大量页面已经驻留。RBRC 的 guard 因而
经常可以执行 Top-50；把少量查询降到 Top-40 或 Top-20，不能再显著减少独立冷页。

这给出一个明确的适用边界：

> RBRC 只有在“候选有一定复用，但固定深度仍造成足够多新增冷页”的中间区间才有空间。
> 复用过低时缓存和状态规划都难受益；复用过高时固定 Top-50 已很便宜，改变深度的边际
> 收益又接近零。

因此“表示生命周期管理”这个问题仍成立，但当前 v0 的 `cold-budget guard` 并不是跨
工作负载普遍占优的最终解。更强的论文方法需要在不触碰 v0 盲测的前提下，解释并利用
这个边界，例如事前 workload admission：预测一个表示栈/工作负载是否值得启用动态
规划；不值得时直接使用强 LFU/GDSF，而不是逐查询执行几乎无收益的 guard。这个想法只
能进入后续 v1，不能回写 v0。
