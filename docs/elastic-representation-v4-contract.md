# Elastic Representation V4: Experimental Contract

## The deeper system insight

An expensive multimodal representation is not only an embedding. Once it has
been computed, it becomes **physical index state with a lifecycle**. For a page
needed by the current query, the system can discard the visual state after use
and pay to recompute it later, or retain it and pay memory cost while waiting
for reuse. This is a rent-versus-retain decision, not a page classification
problem.

This formulation separates two questions that previous ReprForge experiments
mixed together:

1. **activation:** which candidate pages need visual evidence for this query?
2. **retention:** after visual evidence has been computed, which results should
   remain physical index state for future queries?

V4 evaluates only retention. Every policy visually refines exactly the same
BM25 Top-20 candidates, so it cannot change retrieval quality. A positive V4
result must come from lower recomputation plus residency cost, not from
silently skipping difficult pages.

## Position in the current RAG landscape

Current optimization work acts at several different layers:

- [METIS (SOSP 2025)](https://doi.org/10.1145/3731569.3764855) adapts
  per-query RAG configuration and jointly schedules it with inference. Its
  knobs include retrieved chunk count and synthesis method; it does not manage
  the lifetime of document representations.
- [LightSTAR](https://arxiv.org/abs/2606.23539) uses a lightweight visual
  selector followed by expensive refinement of query candidates. This is the
  strongest adjacent **transient-refinement** execution model.
- [MetaEmbed](https://arxiv.org/abs/2509.18095) trains nested multi-vector
  representations so token count can scale at test time. It supplies a useful
  future representation ladder, but not an online cross-query materialization
  policy.
- [Reminisce](https://doi.org/10.1038/s41467-025-60802-5) already establishes
  coarse early exits, compatible intermediate-state reuse, and query-time
  fine refinement across several modalities. ReprForge must not claim that
  progressive embedding or shared-prefix refinement is new.
- [Linear Elastic Caching (CIDR 2025)](https://www.vldb.org/cidrdb/papers/2025/p22-kumar.pdf)
  minimizes miss cost plus memory footprint integrated over time using a ski
  rental connection, GDSF, and learned variants. It directly supplies the V4
  two-state baseline. Ski rental itself is prior art, not ReprForge novelty.

The remaining prospective research node is narrower and concrete:

> Compile an evolving multimodal retrieval workload into elastic physical
> representation state, jointly deciding representation level, activation,
> retention, and eviction from measured quality and physical costs.

V4 does not claim to solve that complete node. It tests whether its simplest
binary retention subproblem has measurable headroom on real document traces.

## Frozen workload and semantics

Use two complete official ViDoRe score traces already generated by the real
BM25 and ColPali paths:

| Dataset | Queries | Pages | Candidate events |
|---|---:|---:|---:|
| ViDoRe HR | 318 | 1,110 | 6,360 |
| ViDoRe Finance | 309 | 2,942 | 6,180 |

For each query, BM25 Top-20 pages form the request batch. Candidate-relative
BM25 plus visual z-score fusion is fixed. Duplicate requests within one query
are charged once.

The physical inputs are measured per-page ColPali encode time and vector
bytes. Let:

- `B_i` be the measured encode time of page `i` in milliseconds;
- `S_i` be its visual state size in MiB;
- `lambda` be an explicit sensitivity parameter in
  milliseconds per MiB per query interval.

The charged cost is

`sum(re-encodes * B_i) + lambda * integral(resident MiB over query time)`.

`lambda` is not presented as a cloud price. V4 sweeps it from 0.1 to 32 to
locate policy boundaries. Per-page times are additive batched-equivalent work,
not an end-to-end latency simulator.

## Policies

1. `no_cache`: visually encode every candidate event, then discard it.
2. `resident`: encode on first touch and retain until the workload ends.
3. `ski_ttl`: retain for the measured break-even interval `B_i/(lambda*S_i)`
   after every access.
4. `verified_ski_ttl`: first use is transient; a second observed use admits the
   page for the same break-even TTL. This is an estimate--verify--commit
   variant that prevents one-off scans from becoming permanent state.
5. `offline_oracle`: with knowledge of the next access, choose independently
   for every gap whether holding or rebuilding is cheaper. It is an
   unattainable lower bound.

The first four use no qrels or future requests. The V4 controller is not a
learned utility model.

## Questions and gates

V4 asks:

1. Is there a nonempty cost regime where an elastic policy beats both fixed
   extremes on both datasets while preserving identical retrieval quality?
2. Does the result survive ten deterministic permutations of benchmark query
   order?
3. How much headroom remains to the offline oracle?

A positive result justifies building a multi-state controller only if the
elastic policy improves over the better fixed extreme by at least 5% on both
datasets in some nontrivial cost regime. It is not sufficient for a paper
claim: ViDoRe ordering is not a production arrival trace, only two corpora are
tested, and the binary controller must still be compared with strong caching
algorithms.
