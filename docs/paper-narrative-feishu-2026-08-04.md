## 0. 先说结论

ReprForge 目前最值得推进的方向，不是泛泛地说“把文本索引和视觉索引解耦”，也不是继续寻找一种对所有数据都安全的统一压缩率，而是研究下面这个问题：

> 当昂贵的多模态索引还没有建完时，RAG 能否先用廉价索引提供可用证据，再根据真实查询逐步构建可复用的视觉表示，并用合理的调度顺序，更早地得到高质量、稳定的证据？

这个问题可以暂时叫作：

> **随用随建的多模态索引编译**  
> Anytime Multimodal Index Compilation

一句话论文主张可以写成：

> ReprForge 将多模态 RAG 的索引构建从“一次性预处理”改造成“可在线推进的编译过程”：廉价文本定位器先暴露查询—页面依赖，Causal Hard Frontier 在仅观察已到达请求和当前索引状态的条件下，联合利用完成成本、局部性和年龄，并用逐请求 hard bypass budget 防止无限越过；完成页面被原子、持久发布，从而改善真实 elapsed 时间上的延迟—工作量—证据质量前沿。

这里真正可能形成贡献的不是某一个模块，而是四件事的组合：

1. 定义“索引尚在构建时，证据质量如何随时间变化”这个问题；
2. 提出面向真实视觉表示构建成本的查询—页面依赖调度方法；
3. 做出可以先服务、再构建、可复用、可回滚的端到端系统；
4. 用质量—时间、证据稳定时间和有害修订等指标，而不只用最终检索分数评价它。

目前第 1--3 点已有完整证据链，第 4 点的检索/证据指标成立但答案级结果失败。强调度基线、有限到达窗口、IRPapers、五域、两种视觉表示、closest-work、结构破坏和成本噪声均已完成。Delay-D32 与 B32 可行域结构等价且只落后约 1%，因此算法 novelty 必须降级；private-pages 消融又把收益降到 0，证明跨查询共享机制确实成立。当前最关键缺口是同一 B32 可行域内的 scoring 单变量消融、真实控制面/GPU 时间和跨检索器原始 trace。

## 1. 术语解释：先把问题说成人话

### 1.1 RAG 是什么

RAG 的中文可以理解为“先检索证据，再让模型根据证据回答”。它一般分成两步：

1. 从知识库中找出和问题最相关的文档或页面；
2. 把这些内容交给大模型生成答案。

如果第一步找错了，第二步的模型再强也容易回答错误。因此，RAG 的“索引”和“检索”不是附属模块，而是决定模型看见什么证据的基础设施。

### 1.2 多模态 RAG 是什么

现实文档不只有纯文本，还有表格、图表、页面布局、示意图、字体和空间关系。多模态 RAG 的目标，是让检索和回答过程同时使用这些文字和视觉信息。

例如，一份财报里的柱状图可能没有被完整转成文字；一张工程图的箭头和相对位置也很难靠普通文本解析保留。如果只做文字检索，这些证据会丢失。

### 1.3 索引是什么

索引不是简单的“把文件放进数据库”。它是系统提前为每个页面算好的一组可搜索表示。

普通文本索引可以记录关键词和词频，构建很快。视觉索引需要把每页文档渲染成图片，再通过视觉语言模型变成向量，通常更慢、更占显存和存储。

### 1.4 多向量视觉表示是什么

ColPali 一类方法不会只用一个向量表示整页，而是给页面中许多局部区域分别保存向量。查询时，问题中的词可以分别和页面中的不同区域匹配。这种做法更能保留表格、布局和局部图像信息，但一页会产生大量向量，构建和存储成本也更高。[ColPali 论文](https://arxiv.org/abs/2407.01449)

### 1.5 后期交互是什么

“后期交互”是指：文档和问题先分别变成多组向量，到检索时才做细粒度比较。它比“每个页面压成一个向量”更精细，但查询时需要比较更多向量。

### 1.6 异构索引是什么

异构索引不是指放了几种数据库，而是同一批文档可能处在不同的物理表示状态。例如：

- 所有页面都有廉价文本索引；
- 热门页面已经有完整视觉表示；
- 部分页面只有压缩视觉表示；
- 新页面的视觉表示还没有构建；
- 某些页面正在构建但还没有对用户可见。

因此，“异构”描述的是索引物理状态不同，而不只是检索分数融合。

### 1.7 索引编译是什么

我们使用“编译”这个词，是因为系统不是简单运行一个编码器，而是在把下面几类输入：

- 原始文档；
- 查询工作负载；
- GPU、内存和时间预算；
- 可接受的质量风险；

转换为下面这些可执行决定：

- 哪些页面先建视觉表示；
- 哪些表示应当复用和保留；
- 哪些查询可以先用文本回答；
- 哪批新表示何时一起发布；
- 索引更新失败时读者看到哪个旧版本。

所以，“编译”只有在系统真的做了物理表示和执行计划的选择时才成立。仅仅把代码模块拆开，不足以支撑这个词。

### 1.8 查询候选组是什么

廉价文本检索会先为每个问题找出一小批候选页面，例如前 20 页。我们把这批页面称为这个查询的“候选组”。视觉模型只需要先构建和检查这些页面，而不是扫描完整语料库。

### 1.9 依赖前沿是什么

每个查询依赖一组候选页面。如果某个查询只差两页就能完成视觉增强，而另一个查询还差二十页，那么先完成前者通常更快得到一个可发布的高质量结果。

同时，如果一页被许多查询共同需要，先构建它可以减少未来重复工作。ReprForge 当前的“候选组前沿调度”综合考虑：

- 一个查询距离完成还缺多少页面；
- 新建页面未来能被多少查询复用；
- 当前已有页面和下一批页面能否形成较好的编码批次。

### 1.10 原子发布是什么

一批页面要么完整构建成功并一起可见，要么失败后完全不发布。用户不会看到一半新、一半旧、难以复现的中间状态。这和数据库事务的直觉类似。

### 1.11 “随时可用”是什么意思

这里的“随时可用”不是说任何时刻都达到最终质量，而是说：

- 一开始就能用文本索引提供初始证据；
- 随着视觉索引逐步构建，证据质量通常继续提高；
- 给系统更多时间或计算预算，结果会逐步接近最终状态。

## 2. 为什么这个问题值得研究

### 2.1 现有论文常常默认“索引已经建好了”

许多 RAG 工作比较的是：索引完成后，检索准不准、查询快不快、生成答案好不好。但是新知识库第一次上线、批量文档更新、模型更换后重建索引时，系统会经历一个很长的“索引未完成”阶段。

对文本索引，这个阶段可能不明显；对视觉多向量索引，它可能成为主要成本。页面需要渲染、视觉编码、存储大量向量，并建立可搜索结构。传统做法要么等全部完成再服务，要么在查询到来时临时计算，导致用户等待且计算难以复用。

### 2.2 视觉索引确实有价值，但代价不能忽略

ColPali 证明了直接对页面图像建立多向量表示可以保留布局、表格和图像信息。[VisRAG](https://arxiv.org/abs/2410.10594) 进一步把页面图像直接用于检索和生成，报告其端到端效果相对传统文本流程有明显提升。M3DocRAG 则把问题扩展到多页、多文档和多种证据形式，并提供了 3,000 多份 PDF、40,000 多页的开放域文档问答基准。[M3DocRAG 论文](https://arxiv.org/abs/2411.04952)

这些工作说明“直接使用视觉文档”是正确的大方向，但也使构建成本更加突出。

### 2.3 只做事后压缩，没有解决第一次构建

压缩可以减少最终存储量和检索计算量，但很多压缩方法仍然要先让视觉编码器处理所有页面。也就是说，最昂贵的第一次视觉编码已经发生了。

ReprForge 前期对统一池化、选择性完整表示、低秩残差和工作负载引导令牌选择做过多轮实验。结果表明：平均质量损失可以很小，但少量查询的尾部损失很大；在 HR、Finance、Industrial、Pharmaceuticals 等领域之间，安全阈值也不稳定。这个负面结果反而加强了当前动机：如果核心痛点是“多久能开始提供有用的多模态证据”，那么研究构建顺序和复用比继续追逐一个统一压缩率更直接。

### 2.4 真实查询会暴露“应该先建什么”

一个文档库的所有页面不一定同样紧急。查询到来后，廉价定位器会暴露查询和页面之间的依赖关系：

- 有些页面被很多问题反复需要；
- 有些查询的候选页面高度重叠；
- 有些查询只差少数页面就能完成视觉增强；
- 有些页面可能一直没人访问。

这使索引构建不再只是“从第一页编码到最后一页”，而成为一个由工作负载驱动的物理计划问题。

## 3. 代表性工作的思路，以及它们与我们的关系

不建议为了“大厂工作”而按公司强行分类。更有用的做法是按它们对问题的判断分类，因为同一家公司内部也可能有完全不同的路线。

### 3.1 路线一：尽量保留原始视觉信息

**ColPali** 的判断是：复杂文档的布局和图表在文字解析中会丢失，因此直接把页面图片编码成多向量表示，再进行细粒度匹配。[论文](https://arxiv.org/abs/2407.01449)

它的主要贡献是新的视觉文档检索范式和 ViDoRe 基准。它解决的是“视觉文档应该怎样表示和检索”，并没有研究“这些昂贵表示尚未建完时，系统怎样服务”。ReprForge 当前使用 ColPali 作为底层表示，不应把 ColPali 本身当作我们的贡献。

**VisRAG** 的判断更进一步：不仅检索阶段直接使用页面图像，生成阶段也让视觉语言模型阅读原始页面，避免文字解析造成的信息损失。[论文](https://arxiv.org/abs/2410.10594)

**VDocRAG** 通过自监督训练，把视觉信息压缩进更紧凑的稠密视觉令牌，并建立开放域视觉文档问答集合 OpenDocVQA。[论文](https://arxiv.org/abs/2504.09795)

这类工作主要优化“表示和模型”，而 ReprForge 更适合固定一个成熟视觉检索器，研究表示的构建生命周期。我们需要在不同视觉检索器上验证机制能迁移，但没有必要同时训练一个全新的基础模型。

### 3.2 路线二：让查询侧规划得更聪明

阿里巴巴相关团队的 **OmniSearch** 认为，复杂多模态问题不能用固定的一次检索完成，因此用规划代理把问题拆成子问题，并动态选择查询、工具和检索轮次。[论文](https://arxiv.org/abs/2411.02937)

**ViDoRAG** 也从查询和推理侧出发，用混合检索、探索、总结和反思组成多轮代理流程。[论文](https://arxiv.org/abs/2502.18017)

这些工作解决的是“一个复杂问题应该怎么查、查几次、用什么工具”。它们通常假设底层索引或搜索工具已经可用。ReprForge 解决的是另一层：当代理决定要访问某页时，如果该页的昂贵视觉表示还不存在，系统应该何时构建、是否保留、如何与其他请求共用。

这两类方法未来可以组合：查询代理产生需求，ReprForge 编译和调度物理表示。但我们不应该在当前阶段把“训练代理”也纳入主贡献，否则问题会过宽。

### 3.3 路线三：把视觉理解推迟到查询时

**DVI（延迟视觉摄取）** 提出“索引用于定位，而不是提前理解全部页面”：预处理阶段只建立元数据和 BM25 等轻量索引，查询到来后才把原始页面交给视觉模型，并逐步缓存结果。[论文](https://arxiv.org/abs/2602.14162)

这是对 ReprForge 最直接的已有工作压力。它说明以下说法已经不够新：

- 先做轻量文本索引；
- 查询时再使用视觉模型；
- 把查询结果缓存起来。

我们的区别必须具体到：DVI 主要把视觉模型用于查询时阅读和回答；ReprForge 构建的是可供未来检索复用的多向量物理索引状态，并研究构建顺序、批处理、原子发布以及整个构建期间的证据质量曲线。最终论文必须通过实验说明，这一层不仅是工程实现细节。

### 3.4 路线四：优化 RAG 服务和缓存

**RAGServe** 根据每个查询的延迟和质量需求，联合调整检索片段数、生成方式和请求调度。[论文](https://arxiv.org/abs/2412.10543)

**RAGCache** 缓存的是大模型读取知识后的中间计算状态，并利用 GPU、主存多级缓存减少首个生成词的等待时间。[论文](https://arxiv.org/abs/2404.12457)

**TeleRAG** 预测后续检索需要的数据，并把 CPU 到 GPU 的数据搬运与生成过程重叠。[论文](https://arxiv.org/abs/2502.20969)

这些系统都说明，RAG 值得做跨阶段调度，而不能只优化单一模型。但是它们主要调度已经存在的检索结果、缓存状态或数据搬运。ReprForge 的特殊成本是：缺失的视觉页面表示必须先经过真实视觉编码才能存在，而且一旦构建，可以成为长期复用的索引资产。

### 3.5 路线五：利用查询重叠减少系统开销

**CaGR-RAG** 会把访问相同磁盘向量簇的查询分组，并预取相关向量簇，从而减少磁盘缓存缺失和尾部延迟。[论文](https://arxiv.org/abs/2505.01164)

这是对当前“前沿调度器”最接近的系统类比。因此，下列内容不能单独作为贡献：

- 把访问相似数据的查询放在一起；
- 利用缓存局部性；
- 预取下一批数据。

ReprForge 要证明的窄区别是：CaGR-RAG 访问的是已有向量，ReprForge 面对的是尚未存在、必须在 GPU 上物理构建的多向量表示；调度目标也不只是查询延迟，而是“单位构建工作能多早让多少查询获得高质量证据”。

### 3.6 AnythingLLM 对我们的价值

AnythingLLM 更适合作为工程动机和原型载体，而不是论文新颖性来源。我们对它的改造说明了实际产品会遇到：

- 文档接入和重建索引时间长；
- 文本、视觉、摘要等表示需要分阶段产生；
- 在线请求与后台构建需要协调；
- 状态必须持久化，失败后不能污染已发布结果。

但私有小语料、单台 5090 和产品侧启发式指标不足以支撑论文普适性。正确用法是：用 AnythingLLM 解释问题从哪里来，并可作为系统演示；正式证据仍应来自公开基准、可复现实验和严格基线。

### 3.7 文献地图的核心结论

| 技术路线 | 代表工作 | 它主要优化什么 | 留给 ReprForge 的空间 |
|---|---|---|---|
| 直接视觉检索 | ColPali、VisRAG、VDocRAG | 表示质量、视觉信息保留 | 昂贵视觉表示怎样逐步构建和复用 |
| 查询规划 | OmniSearch、ViDoRAG | 查什么、查几轮、如何推理 | 物理索引尚不存在时怎样满足查询需求 |
| 延迟视觉处理 | DVI | 查询时才调用视觉模型 | 可复用多向量索引的构建生命周期和质量轨迹 |
| RAG 服务调度 | RAGServe、RAGCache、TeleRAG | 查询配置、生成缓存、数据搬运 | 把“新建索引表示”作为可调度且可积累的工作 |
| 查询分组与局部性 | CaGR-RAG | 已有向量的磁盘访问和缓存命中 | 面向缺失表示构建和证据完成度的调度 |

## 4. 论文真正要定义的问题

### 4.1 传统问题定义

传统索引论文通常问：

> 给定完整索引，怎样在质量、存储和查询延迟之间取得更好的平衡？

这个定义忽略了索引构建阶段。

### 4.2 我们的新问题定义

ReprForge 应该问：

> 给定一个立即可用的廉价定位索引、一批尚未构建的昂贵视觉表示，以及不断到来的查询，系统应按什么顺序构建、复用和发布视觉索引状态，使有限时间内用户获得的累计证据质量最大，同时控制最终构建工作、延迟和有害修订？

输入包括：

- 文档页面集合；
- 已有的廉价文本索引；
- 到达中的查询；
- 每个查询由廉价索引产生的候选页面；
- 当前已构建的视觉页面集合；
- GPU 编码、批处理、内存和时间预算。

系统可做的决定包括：

- 下一批处理哪些查询；
- 下一批构建哪些缺失页面；
- 哪些结果一起发布；
- 哪些视觉表示保留给未来请求；
- 如果资源有限，何时淘汰或降级表示。

输出不是一个静态索引，而是一条随时间演化的状态和证据轨迹。

### 4.3 优化目标

最简单的主目标是“质量—时间面积”：

> 从系统开始服务到比较截止时间，把每个时刻的平均证据质量累积起来，再除以总时间。

直觉上，两套系统最终质量相同，但甲在第 10 秒就让大部分查询得到好证据，乙到第 100 秒才一起完成，那么甲的质量—时间面积更高。

可以用一个简单公式表达：

`质量—时间面积 = 在 0 到 T 之间对证据质量 Q(t) 做时间平均`

公式只是帮助把问题说清楚，不应把论文变成纯数学优化。真正难点来自：

- 视觉表示要在真实 GPU 上构建，成本受批次形状和填充影响；
- 调度时不能看到测试集相关性标签，也不知道视觉增强一定有益；
- 页面可以跨查询复用，构建一次会改变未来成本；
- 新结果可能让个别查询变差；
- 失败和并发读取需要明确的版本语义。

因此，这是一个以系统机制为主、优化形式化为辅的问题。

### 4.4 调度器允许看什么

为了避免“用答案指导调度”，当前调度器只允许使用：

- BM25 给出的候选页面；
- 哪些页面已经构建；
- 查询还缺多少页；
- 页面在当前等待窗口中被多少查询需要；
- 实际页面构建工作量和批处理状态。

它不允许使用：

- 测试相关性标签；
- 完整视觉索引产生的分数；
- 每个查询最终会提升多少质量；
- 测试答案是否正确。

这就是“无相关性标签调度”的含义。

## 5. ReprForge 当前方法

### 5.1 系统流程

1. 为所有页面建立廉价 BM25 文本定位器；
2. 查询到来后，先返回或准备基于文本的初始证据；
3. 为每个查询取前 20 个候选页面，形成查询—页面依赖图；
4. 检查哪些候选页面已经有视觉表示，哪些仍然缺失；
5. 前沿调度器优先选择接近完成、且页面复用收益较高的查询批次；
6. 在 A100 上批量构建缺失页面的 ColPali 多向量表示；
7. 对候选组做视觉评分，并与文本分数归一化融合；
8. 只有完整批次成功后，才原子发布新证据和新索引状态；
9. 已构建视觉状态被保留，后续查询可直接复用。

### 5.2 原始前沿调度器的直觉

调度器不是预测“哪个页面语义最重要”，而是在可观测信息上近似解决两个问题：

- **尽快闭环：** 优先完成只差少量页面的查询，让更多查询早些获得完整视觉候选组；
- **尽量复用：** 优先构建会被多个等待查询共同使用的页面，让一次编码服务更多请求。

这比单纯按到达顺序更聪明，也比只按页面全局热门程度更能适应当前已构建状态。

### 5.3 当前主方法：Causal Hard Frontier

原始 frontier 在 unique-page 质量效率上强，但强 CaGR locality 在 Finance 的 mean sojourn 和 charged work 上反超。软年龄、软绕过和 deadline tie-break 又无法同时保护尾部。最终方法不再声称一个软分数通吃，而是明确组合两层：

1. **因果效用：** 只用已经到达 query 的 locator cohort、当前 compiled/LRU、arrival age 和 rank，估计下一 query 的 completion/locality 成本；不接收 qrel、未来 arrival 数组或 EOS；
2. **硬顺序预算：** 任一等待 query 最多被 32 个更年轻 query 越过。每个 batch slot 都检查约束并立即更新 bypass counter，最老 pending 永远可行。

独立事件驱动实现与 B32 reference 在 HR/Finance 20/20 cell 的 dispatch、elapsed tuple、physical work、cache/union、bypass 和 publication trace 全部精确一致。跨五域十个到达 cell 的 median sojourn/work/elapsed-quality ratio 为 0.923/0.949/0.948，9/10 cell 至少一轴改善 5%，10/10 P99 更优。

### 5.4 当前尚未实现或尚未证明的部分

- 因果方法固定 W=64、batch 8 和 B=32；还不能扩张到低队列深度、任意 batch 或所有 arrival regime；
- bypass 是可证明 ordering guarantee，不等同于所有用户子群公平。反事实 slowdown 的 pooled P95/P99 已通过，但仍存在单 query max 反例；
- 当前完成视觉候选组后直接发布；严格交叉验证的安全发布器能减少约 44%--46% 有害修订，但仅保留 77.5%--79.3% 正收益，尚未达到冻结门槛；
- 当前状态是不设容量上限的主存驻留，不是完整的磁盘/显存分层索引；
- 三层答案实验已完成且严格 NO-GO，论文只能主张 retrieval/index-system contribution；
- ColModernVBERT 已证明原始 frontier 跨表示，但本机缺少可供 B32 重放的原始 Modern trace，因此当前因果方法仍未单独跨 retriever 验证；
- 还没有证明对更新、删除和模型版本切换同样有效。

## 6. 当前实验结果怎样写进论文

### 6.1 端到端候选组编译结果

底层模型为 ColPali-v1.1，硬件为单张 A100-SXM4-80GB。文本定位器为 BM25，每个查询取前 20 个候选页面。

| 数据集 | 完整视觉索引 | ReprForge 先进文本后视觉 | 构建的视觉页面 |
|---|---:|---:|---:|
| ViDoRe v3 HR | 108.74 秒，nDCG@10 = 0.51778 | 98.03 秒，nDCG@10 = 0.53729 | 895 / 1,110 |
| ViDoRe v3 Finance-EN | 320.83 秒，nDCG@10 = 0.47316 | 190.50 秒，nDCG@10 = 0.56280 | 1,855 / 2,942 |

这里可以说：在这两个数据集上，候选组编译器比完整视觉预构建更快，并通过文本—视觉融合得到更高的最终 nDCG@10。

但不能说：ReprForge 在所有质量指标上全面支配完整视觉索引。HR 的 Recall@100 比完整视觉低 0.02245，而且最终构建覆盖率仍然达到语料的 63%—81%，并不是极低成本方案。

### 6.2 调度器的精确工作量回放

所有调度顺序最终构建同一批候选并集页面，只改变构建和发布顺序。

| 数据集 | 到达顺序平均完成页数 | 静态热门顺序 | 前沿调度 | 前沿相对到达顺序 |
|---|---:|---:|---:|---:|
| HR | 718.6 | 593.5 | **579.8** | 减少 19.3% |
| Finance-EN | 1,208.7 | 893.8 | **861.4** | 减少 28.7% |

“平均完成页数”是指一个查询得到完整视觉增强时，系统累计已经构建了多少个不同页面。越低说明有用查询越早完成。

### 6.3 HR 的真实 A100 调度结果

| 顺序 | 总时间 | 第一批结果 | 批次 P95 | 最终 nDCG@10 |
|---|---:|---:|---:|---:|
| 到达顺序 | 98.03 秒 | 15.54 秒 | 9.04 秒 | 0.53729 |
| 静态热门顺序 | 99.26 秒 | 12.26 秒 | 4.66 秒 | 0.53705 |
| **前沿调度** | **91.85 秒** | **6.73 秒** | **4.52 秒** | 0.53648 |

使用冻结分数重放证据轨迹后：

| 顺序 | 构建期间平均 nDCG | 相对公平完整预构建的收益 | 达到 90% 最终融合收益的时间 | 证据稳定时间 P50 |
|---|---:|---:|---:|---:|
| 到达顺序 | 0.49841 | +0.01340 | 98.02 秒 | 82.01 秒 |
| 静态热门顺序 | 0.50708 | +0.02199 | 94.31 秒 | 72.98 秒 |
| **前沿调度** | **0.50792** | **+0.02277** | **86.67 秒** | **64.25 秒** |

这个结果的意义不是只把“容易但低质量的问题”提前了。前沿调度在质量—时间指标上也略好于静态热门顺序。

### 6.4 Finance 的真实 A100 迁移结果

| 顺序 | 总时间 | 第一批结果 | 批次 P95 | 最终 nDCG@10 | Recall@100 |
|---|---:|---:|---:|---:|---:|
| 到达顺序 | 190.50 秒 | 15.98 秒 | 9.13 秒 | 0.56280 | 0.88045 |
| **前沿调度** | **172.85 秒** | **4.85 秒** | **8.02 秒** | 0.56255 | 0.88045 |
| 静态热门顺序 | 171.36 秒 | 6.20 秒 | 6.85 秒 | 0.56275 | 0.88045 |

前沿调度相对到达顺序减少 9.3% 总时间，第一批发布提前 69.6%。但静态热门顺序的最终完成时间比前沿再快约 0.9%，批次 P95 也更低。前沿的优势体现在更早发布有用质量：第一批比静态热门提前 21.7%，达到 90% 最终融合收益的时间为 128.11 秒，而静态热门为 156.22 秒；构建期间平均 nDCG 分别为 0.55401 和 0.55356。三种顺序的 Recall@100 不变。

这组结果说明论文不应声称“前沿在所有延迟指标上全面支配”。更准确的结论是：前沿调度改善证据质量轨迹，即使一个简单热门度顺序可能略早完成最后一批。

### 6.5 必须主动报告的反例

视觉增强并不保证每个查询都变好。在冻结回放中：

- HR 约 19.2% 的查询在文本结果切换到融合结果后 nDCG@10 下降；
- Finance 约 22.0% 的查询下降；
- 最差 5% 查询的变化分别约为 -0.116 和 -0.183。

这意味着“更快发布视觉结果”还不等于“更安全地发布答案”。有害修订不是要隐藏的噪声，而可以成为论文中的一个新问题：系统何时应该发布新证据，何时应该保留旧证据或标记不确定性。

### 6.6 数值可复现性说明

冻结视觉分数下，不同调度顺序可以证明最终候选覆盖和排序语义一致。但真实 bf16 编码会因为页面被装入不同批次而产生很小的数值变化；HR 三种顺序的 nDCG@10 跨度为 0.00081。

论文中应分别表述：

- 冻结分数证明逻辑语义和候选覆盖不随顺序变化；
- 真实模型存在批次相关的浮点数值波动，不能声称逐位相同。

### 6.7 强调度基线和敏感性

第一轮补充了随机顺序、静态热门度、只按候选重叠分组、最短缺失候选组、只看复用，以及乐观离线工作贪心。在 K=20、请求批次 8 的冻结回放中：

- HR 前沿平均完成工作为 579.8 页，优于静态热门度 593.5、重叠分组 596.5、最短缺失 583.4，距离离线贪心 571.7 仅 1.4%；
- Finance 前沿为 861.4 页，优于静态热门度 893.8、重叠分组 893.7、最短缺失 901.2，距离离线贪心 850.9 仅 1.2%；
- 在 K={10,20,50}、请求批次={1,4,8,16} 的 12 个组合里，前沿在两个领域都 12/12 胜过热门度/重叠类方法的平均工作量。

因此当前收益不能简单解释成“把相似查询放在一起”或“先做热门页面”。但 HR 的静态热门度具有更高的事后质量—工作 AUC，说明工作效率和证据价值是两个不同目标。

### 6.8 有限窗口和公平性边界

在五个固定查询排列、burst/Poisson 两类到达模型下，W=32 前沿相对 FIFO 的平均完成工作下降为：HR 10.6%/7.0%，Finance 14.7%/14.5%，四种设置的质量—工作 AUC 都高于 FIFO。

但严格门槛要求 W=32 至少保留完整队列一半收益。突发流量只达到 HR 49.5%、Finance 48.7%，因此结论必须记为 NO-GO。W=64 四种设置保留 72.9%--100%，可以支持“具有足够排队深度的并发或批量工作负载”，不能扩张成任意低负载在线服务。

无约束 W=32 的饥饿比例为 13.3%--20.1%；一次性硬公平上限能降到 0%，却只能保留 22.0%--46.2% 完整队列收益。下一方法问题因此是连续的效率—公平折中，而不是是否添加一个 FIFO 兜底。

第二轮又预注册了年龄连续加分、软绕过预算和双队列配额共 26 个配置。没有一个同时通过收益、AUC 和 5% 饥饿门槛。能把饥饿压到 5% 以下的 HR 年龄权重只保留 19.1%--42.5% 收益，并且迁移到 Finance 后饥饿又升到 14.7%。因此不再继续搜索同类权重；如果重开，应采用真实截止期或拆分原子发布结构。

### 6.9 第三个基准 IRPapers

恢复的完整分数面包含 180 个查询和 3,230 个页面。BM25 Recall@5 为 78.3%；候选相对的 BM25+ColPali 融合在 K=20 达到 82.2%。在所有调度最终并集均为 987 页、最终质量相同的前提下：

- FIFO 平均完成工作 656.1 页；
- 静态热门度 451.1 页；
- 前沿 443.1 页，相对 FIFO 降低 32.5%，相对热门度降低 1.8%。

K=50 时前沿相对热门度的优势扩大到 5.1%；K=10 时则比热门度差 5.5%。这和两个 ViDoRe 领域共同指向一个边界：候选组越大，动态常驻状态越重要；很小的候选组可由全局热门度解释。

IRPapers 也给出一个重要反例：前沿的质量—工作 AUC 为 0.81654，略低于热门度的 0.81785。前沿更快完成查询，却不一定先完成会产生正质量修订的查询。因此下一轮要联合“复用价值”和无标签的“预期证据价值”，不能偷偷用相关性标签调顺序。

### 6.10 安全发布器的严格负结果

严格嵌套、查询级交叉验证下，当前发布器在 HR/Finance 分别减少 44.3%/45.6% 有害修订，同时保留 77.5%/79.3% 正收益，平均 nDCG 仍高于 BM25。由于预注册要求两个领域都保留至少 80%，结论是 NO-GO。

这条线有可测的 oracle 空间，但现有排名一致性、分数间隔和归一化统计不足以形成可靠安全证书。为了尽快固化主线，暂不把安全发布器列为已完成贡献，而作为局限和后续问题。

### 6.11 价值感知调度的跨域负结果

为了弥补“工作最省不等于证据价值最高”，第二轮尝试仅用 BM25 熵、候选边界间隔和复用状态预测调度价值。方法只在 HR 选择参数，Finance 和 IRPapers 完全冻结。

HR 训练内同时大幅改善工作和 AUC，Finance 也通过门槛，但 IRPapers 的 AUC 比静态热门度低 0.001591。消融显示，Finance 去掉价值项只改变 0.000009 AUC，IRPapers 去掉价值项反而更好。结论是当前 BM25 不确定性不是可迁移的证据价值代理，论文继续保留工作前沿，不增加价值感知主张。

### 6.12 统一 anytime 度量

为了让 895、1,855、987 页和不同质量指标可比较，统一结果增加了：归一化质量遗憾面积、持续达到最终增益 50%/90% 的工作比例、10%/25%/50%/75% 固定预算质量、完成工作 P50/P95 和尾部公平指标。

前沿在 HR、Finance、IRPapers 三域的平均查询完成工作都最低，相对 FIFO 的质量遗憾也都更低；但遗憾最低只在 Finance 属于前沿，HR 和 IRPapers 都由静态热门度领先。这进一步固定了论文措辞：前沿改善完成工作并具有竞争力的质量轨迹，不是全数据集全指标最优。

## 7. 论文贡献应该怎样写

### 7.1 不能单独算贡献的内容

以下内容可以是设计组成，但单独看都不够新：

- 把文本检索和视觉检索解耦；
- 异步执行或后台任务；
- 普通缓存和批处理；
- 使用 BM25 做第一阶段召回；
- 使用 ColPali 做视觉检索；
- 文本分数和视觉分数融合；
- 查询到来后再调用视觉模型；
- 把候选重叠的查询放在一起；
- 做索引版本号和原子更新。

所以你的判断是对的：**解耦本身不是 contribution，它是让后续机制成立的 design idea。**

### 7.2 可以争取成为论文贡献的写法

当前贡献可以压缩成三条：

1. **问题与评价：** 我们提出“随用随建的多模态索引编译”问题，把评价对象从索引完成后的静态质量，扩展到索引构建期间的证据质量、稳定时间、构建工作和修订风险。
2. **机制：** 我们实例化 Causal Hard Frontier：一个不接收 qrel 或未来请求的事件驱动策略，在与 Delay-D32 等价的 bounded-overtaking 可行域内，利用 compiled/LRU 状态上的 normalized completion 与 continuous age 降低构建和重载工作。贡献不在 hard bypass 本身。
3. **系统与实证：** 我们实现具有持久复用状态和原子发布语义的端到端系统，并在五个视觉文档域、两类到达模型和三条物理质量时间轴上验证：冻结方法的跨 cell median sojourn/work/elapsed-regret ratio 为 0.923/0.949/0.948，10/10 P99 更优；同时报告 unique-page 质量和单 query max 的反例。

如果加入安全发布机制并验证成功，可以有第四条：

4. **安全修订：** 我们识别并测量多模态增强导致的有害证据修订，提出无需测试标签的发布或保留策略，降低答案反复和质量尾部风险。

第四条有潜力，但目前没有方法证据，不应提前写成已完成贡献。

### 7.3 论文最核心的“新东西”到底是什么

最窄、最可守住的表述是：

> **带逐请求硬顺序保证的因果表示编译调度。**

一般查询调度是在已有数据和已有模型上分配请求；ReprForge 把“昂贵且可长期复用的检索表示尚未存在”纳入调度状态，并用证据完成度而不是单纯吞吐量定义收益。

这个点既不是纯模型，也不是纯缓存，更不是纯数学。它是一个跨检索质量和系统物理构建的机制。

## 8. 论文“八股”可以怎样展开

### 8.1 标题候选

主选：

> **ReprForge: Anytime Compilation of Reusable Multimodal Indexes for RAG**  
> ReprForge：面向 RAG 的可复用多模态索引随用随建

更强调故事的备选：

> **Serve First, Compile Along the Way: Progressive Multimodal Indexing for RAG**  
> 先服务，再编译：面向 RAG 的渐进式多模态索引

暂时不建议把 “Heterogeneous” 放到标题中心。除非后续真正实现并评价多种表示级别、容量淘汰和更新，否则当前系统的核心是“缺失/已构建”两种状态，异构性还不够丰富。

### 8.2 摘要草稿

> 视觉文档 RAG 能保留表格、布局和图表信息，但完整构建多向量视觉索引需要昂贵编码。现有工作主要评价索引完成后的查询，较少研究新库接入期间：到达查询如何暴露可复用页面需求、构建完成如何改变后续可用证据，以及怎样同时控制工作量和尾部。我们提出 ReprForge，将多模态索引构建建模为在线渐进编译。系统先用廉价文本定位器产生查询—页面依赖，再由 Causal Hard Frontier 仅依据已到达请求和当前索引状态调度缺失表示；它联合 completion/locality 效用与逐请求有界越过，并原子持久发布新状态。我们区分 elapsed time、charged work 和 unique compiled pages 三条质量轴。独立因果实现与有利 B32 reference 在 20/20 replay cell 完全等价；冻结到五个 ViDoRe 域后，跨 cell median sojourn、work 和 elapsed-quality regret ratio 为 0.923、0.949 和 0.948，且 10/10 P99 优于强 endpoint。真实 A100 实验进一步验证渐进构建可行。结果表明，在线表示构建的共享结构与逐请求服务保证可以共同优化，但 unique-page 质量、跨检索器和真实异构成本仍构成边界。

这版摘要只能称为“工作摘要”。在投稿版本中还需要补上在线到达、答案质量和第三数据集，并与最强在线基线比较。

### 8.3 引言五段式

**第一段：视觉文档 RAG 为什么重要。** 现实知识库包含表格、图表、布局和图片。文本解析会丢失重要证据，直接视觉检索已经显示出明显质量优势。

**第二段：现有评测遗漏了什么。** 当前论文大多默认视觉索引已经完成，只比较完成后的质量和延迟。但在新语料接入、持续更新或切换模型时，对全部页面做视觉编码可能成为最长阶段。在它完成前，系统要么无法服务，要么每次请求重复付出昂贵成本。

**第三段：直观办法为什么不够。** 事后压缩没有消除第一次完整编码；纯查询时视觉理解难以积累可检索状态；普通缓存只决定已有对象留不留下；查询分组只优化已有向量访问。真正缺少的是把查询需求转成可复用视觉表示的构建计划，并评价构建过程中证据何时变得可用。

**第四段：我们的观察和方法。** 廉价文本定位器不仅提供初始答案，还暴露查询—页面依赖图。候选组之间存在重叠，调度顺序会改变构建、重载和证据发布时间；只追求局部性又会无限绕过孤立请求。Causal Hard Frontier 因此只基于已到达需求选择低完成成本、高复用的候选，同时给每个请求一个硬的 younger-bypass 上限。

**第五段：结果和贡献。** 概括问题定义、因果 hard-budget 系统策略、原子可复用状态，以及五域 median ratio、10/10 P99、private-pages 收益归零和成本噪声四类数字；同时主动说明 Delay-D32 只差约 1%、unique-page 质量与单 query max 反例。

## 9. 完整实验矩阵

### 9.1 数据集

最低配置建议：

- ViDoRe v3 HR：现有开发数据；
- ViDoRe v3 Finance-EN：现有跨领域迁移；
- 第三个更大或不同结构的公开视觉检索数据集：优先选择 MIRACL-VISION、ViDoRe 其他语言/领域，或能进行开放域检索的 M3DocVQA；
- 一个答案级视觉文档问答集合：M3DocVQA、OpenDocVQA 或 MMDocIR 中适合生成评价的子集；
- 一个有真实或可辩护到达分布的工作负载。若没有视觉 RAG 公共时间戳，可明确把公开 RAG 轨迹的到达间隔映射到视觉查询，但要说明这只是到达模型，不伪装成原生视觉日志。

数据集不宜一次铺十个。比起很多小表，三个领域的完整端到端证据更重要。

### 9.2 必须包含的基线

质量基线：

- 仅 BM25；
- 完整 ColPali 视觉预构建；
- BM25 与完整视觉融合；
- 查询时临时视觉编码、但不保留状态；
- DVI 风格的查询时页面阅读方案，如实现和数据允许。

调度基线：

- 按查询到达顺序；
- 随机顺序，多次种子；
- 静态页面热门度；
- 只按候选重叠分组的 CaGR-RAG 风格基线；
- 只看“还缺多少页面”；
- 只看“未来可复用次数”；
- 当前完整前沿调度。

系统基线：

- 无跨请求复用；
- 普通最近最少使用缓存；
- GDSF 一类同时考虑对象大小、代价和频率的强缓存策略；
- 有限容量下的前沿调度加保留策略。

静态热门度如果使用完整未来查询统计，应明确标成“知道未来的乐观基线”，不能当作普通在线算法。

### 9.3 指标

最终检索质量：

- nDCG@10：前十页的相关性排序质量；
- Recall@100：前一百页覆盖了多少相关页面；
- 文档级和领域级宏平均，防止大文档或大领域支配结果。

构建成本：

- 构建的不同页面数；
- 页面构建事件数；
- 视觉编码器调用次数；
- GPU 秒数和端到端时间；
- 持久向量字节数；
- 数据搬运量。

过程质量：

- 第一份文本证据时间；
- 第一批视觉增强证据时间；
- 达到最终质量收益 50% 和 90% 的时间；
- 质量—时间面积；
- 查询证据稳定时间 P50/P95；
- 改善、不变和变差的查询比例；
- 最差 5% 查询的修订损失。

答案级指标：

- 首次正确答案时间；
- 最终答案准确率；
- 引用页面是否正确；
- 答案在后续修订中是否改变；
- 从正确变错误的比例；
- 有证据支持但模型未使用、以及无证据却生成断言的比例。

RAGChecker 提供了检索与生成模块的细粒度诊断思路，可以借鉴其“不要只给一个总分”的原则。[RAGChecker 论文](https://arxiv.org/abs/2408.08067)

### 9.4 统计规范

- 检索质量使用查询级配对自助法置信区间；
- 调度顺序至少使用 3—5 个随机排列，避免官方数据行顺序成为结论；
- 墙钟时间至少重复 3 次，报告中位数和波动；
- 在线到达至少测试不同负载强度；
- 分别报告文档宏平均和查询微平均；
- 所有阈值在 Finance 或第三数据集最终评测前冻结；
- 不要用测试相关性标签调调度参数。

### 9.5 消融实验

需要回答“收益到底来自哪里”：

- 去掉持久复用；
- 去掉动态前沿更新；
- 只用完成度；
- 只用复用度；
- 去掉批处理；
- 改变候选数 K；
- 改变请求批次和图像批次；
- 改变在线观察窗口 W；
- 原子发布对比逐页可见；
- 文本、视觉和融合三种发布路线；
- 容量无限对比有限容量；
- 冷启动对比已经积累一部分状态的热启动。

## 10. 接下来最重要的四道验证门

### Gate A：补齐两领域最强调度基线

**状态：已完成，GO。** Finance 静态热门 A100 结果已恢复；冻结工作回放也加入了热门度、重叠分组、最短缺失、只看复用和离线工作贪心。前沿在两个领域主设置下具有最低的可行非 oracle 平均完成工作，并在 24 个 K/批次组合中全部胜过热门度/重叠解释。

需要保留的限制是：HR 的热门度质量—工作 AUC 更高，Finance 的热门度最终时间和 P95 略好，因此结论是帕累托竞争，而不是全指标支配。

### Gate B：从完整未来重排走向在线窗口

**状态：W32 严格 NO-GO，W64 GO。** 已完成 W={1,8,16,32,64,full}、五个查询排列和 burst/Poisson 回放。W32 在两个突发流量设置分别保留 49.5%/48.7% 完整队列收益，刚低于冻结的 50%；W64 四种设置全部通过。

当前方法还出现 13.3%--20.1% 的严格饥饿事件。第二轮 26 个软公平配置也全部严格 NO-GO。因此论文现阶段应定位为批量知识库 onboarding、有队列深度的并发租户或分析负载，不声称一般在线 serving。

### Gate C：答案级“首次正确”和修订安全

**状态：严格 NO-GO。** 已完成 180 问 gold-page 到达代理、24 问真实自由生成、8 问 7B 格式修复、48 问结构化引用和 48 问盲化语义 judge。接口约束可以做到 100% 合法引用，但 final Top-3 的条件 gold 选择只有 46.7%；盲化语义正确率 initial/final 都是 75.0%，正负修订各 2.1%。Frontier 的语义 restricted-mean work 相对 FIFO 只改善 4.85%，略低于预注册 5%，且差异完全由一条错→对查询驱动。

因此当前论文必须收缩为检索/索引系统，不能写“更早答对”“改善端到端 RAG”或“安全持续发布更好答案”。

### Gate D：第三数据集和现代检索器

**状态：跨领域和跨表示均 GO。** 除 HR/Finance/IRPapers 外，新增 Computer Science、Industrial、Pharmaceuticals 三个 ViDoRe v3 完整域；K20/B8 下前沿相对 FIFO 分别少 18.2%/29.8%/21.6% 平均完成工作，三域均优于热门度。ColModernVBERT 在 HR/Finance 上也分别保持 19.31%/28.74% 的工作下降和更高的质量—工作 AUC，最终候选并集与质量语义一致。

控制面规模实验完成 216/216 组合，精确增量实现比 naive 快 17.45×；10K 查询、338K 页面锚点低于 0.92 秒和 116 MiB，30K 压测低于 4.1 秒和 300 MiB。这里的 338K 是依赖图控制面压力，不替代真实大语料视觉编码。

## 11. 如果四道门通过，论文故事如何固化

最后论文应当围绕一个中心图展开：横轴是从系统开始运行后的时间，纵轴是当前用户可获得的证据或答案质量。

- 完整视觉预构建：长时间只有文本基线，到全部建完时质量突然上升；
- 查询时临时视觉：单个请求可能变好，但重复付费且难以积累；
- 到达顺序渐进构建：质量逐步上升，但很多共享机会被浪费；
- ReprForge：更早完成可复用候选组，曲线更快上升并更早稳定。

这张图比“系统有五个模块”更能解释论文贡献。

论文的主结果表则应同时放：

- 最终 nDCG/Recall；
- 首次正确或首次视觉证据时间；
- 达到 90% 最终收益的时间；
- 质量—时间面积；
- 构建页面和 GPU 秒数；
- 有害修订率。

这样审稿人无法只用“最后质量差不多，所以只是工程”来否定，因为问题本身评价的是构建过程。

## 12. 如果某道门失败，怎样调整而不是反复换方向

### 情况一：在线窗口下调度收益消失

把应用场景收窄为“新知识库批量接入”和“周期性大规模更新”，不再声称处理任意在线请求。此时完整队列是合理输入，论文仍可研究批量索引编译。

### 情况二：检索更早，但答案没有更早正确

把贡献限定为视觉文档检索系统，并分析生成模型为什么没有利用更好的证据。不要强行包装成端到端 RAG 提升。

### 情况三：静态热门一直和前沿调度一样好

这说明动态完成度没有提供额外价值。可以把重点转向“工作负载预测与物理复用”，但必须加入漂移、突发热点和更新，使动态状态真正有用；否则调度算法不够形成主贡献。

### 情况四：BM25 漏掉大量纯视觉证据

轻量定位器不能只用 BM25。可以加入便宜的单向量视觉定位器或 OCR 布局特征，形成多级定位器。但这属于底层增强，不要立刻把论文变成新检索模型训练。

### 情况五：有害修订严重

这不是立即放弃方向的理由。相反，可以把“证据发布控制”提升为方法部分：比较旧证据和新证据的一致性、排名边界、跨表示共识或回答置信度，决定自动发布、并排展示还是暂缓发布。但只有找到无需测试标签且可迁移的规则后，才能称为贡献。

## 13. 当前阶段的研究判断

### 13.1 为什么值得继续

- 它直接回到最初最真实的动机：多模态索引构建慢；
- 已经有真实 A100 端到端系统，不只是离线公式；
- 五个 ViDoRe v3 域、IRPapers 和两种视觉检索器上都有方向一致的工作量收益；
- 精确增量控制面在 30K 查询压力下仍低于 4.1 秒和 300 MiB；
- 已经定义出传统静态检索指标没有覆盖的过程指标；
- 相关工作很接近但尚未完全覆盖“构建可复用视觉检索表示时的证据调度”。

### 13.2 为什么现在还不能过度自信

- 原始 frontier 的完整未来工作负载漏洞已由独立因果 API 关闭，但固定 W64/B32 仍限定工作负载范围；
- 三层答案级结果严格失败，论文只能定位为检索/索引系统；
- EdgeRAG 已覆盖按需嵌入生成与跨请求缓存，DVI 和 CaGR-RAG 分别压住“延迟摄取”和“查询分组”两边的新颖性；
- hard bypass、delay scheduling 和 locality-aware fairness 也有经典前作，算法新意不能只写 B32；
- 最终视觉覆盖仍高，必须诚实解释收益来自更早可用和融合质量，而不是极端稀疏索引；
- 五域 replay、fair-locality adaptation、结构消融与 A100 per-page 成本噪声均已完成；但 Delay-D32 太接近，且当前成本 truth 仍是加法 proxy，不是并发 wall-clock；跨检索器 B32 trace 仍未关闭。

### 13.3 我建议的优先级

强基线、有限窗口、答案、跨域、跨表示、控制面规模和 novelty gate 均已完成。原始 frontier 被 bounded CaGR 反超后，60 点软 oracle 揭示显著效率余量但无法满足 hard ordering；固定效用加 B32 后出现唯一可行点。独立 Causal Hard Frontier 又在 20/20 reference cell 精确物化，并在五域取得 median 0.923/0.949/0.948 与 10/10 P99 安全。

因此主方法方向已从“继续找 scheduler”收敛为固定 Causal Hard Frontier，但投稿定位要更诚实：这是在线表示编译系统中的状态感知 policy，不是全新 fairness scheduler。下一优先级只保留三项：固定同一 B32 可行域的 completion-only/age 单变量消融；增量成本缓存与 scheduler CPU/真实 GPU 比例；跨 retriever 原始 trace。任何新实验都不得重调 B32 或软权重。

## 14. 用于组会的一页版

### 问题

视觉文档 RAG 的高质量索引构建昂贵。现有工作主要研究索引完成后的质量和延迟，但实际系统在新库接入和更新时，需要很长时间才能获得完整视觉索引。

### 核心想法

先用廉价文本定位器暴露候选页面需求。Causal Hard Frontier 只看已到达 query 和当前 compiled/LRU，在 completion/locality 收益与 age 之间调度，同时保证任何请求最多被 32 个更年轻请求越过；成功批次被原子、持久发布。

### 与已有工作的区别

- 不训练新的视觉检索基础模型；
- 不只是在查询时临时看图；
- 不只优化已有向量的缓存或磁盘访问；
- 研究的是昂贵视觉表示尚未存在时，怎样构建并尽早发布高质量证据。

### 当前结果

- 五个 ViDoRe v3 域上平均查询完成工作相对到达顺序减少 18.2%--29.8%；
- ColModernVBERT 在 HR/Finance 上仍分别减少 19.31%/28.74%；
- 真实 A100 总时间减少 6.3% 和 9.3%；
- 第一批视觉证据提前 56.7% 和 69.6%；
- 精确增量调度比 naive 快 17.45×，30K 查询控制面低于 4.1 秒；
- 独立 causal API 在 HR/Finance 20/20 cell 与 B32 reference 全量精确等价；
- 五域 median sojourn/work/elapsed-regret ratio 为 0.923/0.949/0.948，9/10 cell 有 5% 效果，10/10 P99 更优；
- Delay-D32 median 只落后约 0.7%--1.1%，说明 B32 本身不是算法新意；
- private-pages 消融后工作收益精确变 0，证明跨查询共享是必要机制；
- A100逐页成本 proxy 下 unit-count 与 CV=0.5 噪声仍过门，CV=1 与系统性低估会吃掉收益；
- 最终候选覆盖基本一致，但真实 bf16 有小幅数值波动；
- 答案语义正确率没有提升，约 19%—22% 查询存在有害检索修订。

### 最大风险

答案级收益失败；EdgeRAG 已覆盖宽泛按需索引生命周期，CaGR 覆盖共享访问分组，Delay Scheduling/DLPM 覆盖 bounded skip 与 locality/fairness。Delay-D32 与 B32 feasible set 结构等价且性能很接近。Causal Hard Frontier 的可守价值来自“会持久改变检索证据的在线表示编译问题 + compiled/LRU completion-age policy + 严格因果接口 + 多物理轴实证”的组合。跨 retriever 和真实并发成本仍未验证。

### 下一步

固定 B32 和全部常数，不再调 scheduler。只补同一 feasible set 的 scoring 消融、控制面优化/真实 GPU 比例和跨 retriever trace；随后立即固化主表与论文，不再扩张新模块。

## 15. 最终建议

不能把“异构索引编译”“查询驱动构建”或 hard bypass 单独写成新颖性。更稳的具体切口是：

> 到达中的 RAG 查询暴露重叠页面表示需求；构建/重载会改变持久、渐进发布的多模态检索索引。Causal Hard Frontier 在严格因果信息下联合优化 completion/locality 与 elapsed evidence quality，并给每个请求有界越过保证。

解耦、缓存、批处理、原子更新、查询分组和 bounded skip 都是已知组成。可守的贡献是新状态语义、因果 hard-budget 调度实例、三轴 anytime 测量与五域物理证据链。完整决策与所有正反结果见 `docs/paper-decision-after-p0-2026-08-04.md`。
